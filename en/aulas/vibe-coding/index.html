Lesson 3 · 20 min

Vibe coding from the trust side: build an app and look for the flaws

Vibe coding means asking for a program in plain language and letting AI write the code. It works: in minutes you get an app that opens and looks finished. The catch is that "it opened" doesn't mean "it's safe." In this lesson you build a one-screen app, safely, and then switch roles: you become the one who looks for the flaws.

Start the lesson

In this lesson you will

  1. 1Build a 1-screen app with Claude Code, Codex, or ChatGPT
  2. 2The rules for practicing without risk
  3. 3Test as a user and as someone trying to abuse it
  4. 4Ask AI for an audit and check it yourself

Goal: build a 1-screen app with AI that runs on your computer, and list 3 flaws you found in it, with the location of each.

01 · The cycle for building with trust

Building is the easy half. The other half is looking for what breaks.

Fixed it? Search again: the fix may break something else
Click each step.

The app that "opened" is the start of the check, not the end.

02 · Step-by-step practice

Pick a path: Claude Code, Codex, or ChatGPT. The rest is the same.

1. Prepare

Create a folder just for the test, for example teste-horizonte. Use only made-up customers and the fake key CHAVE-DE-TESTE-123.

Do not publish anything: the app runs only on your computer, by opening the file in the browser.

2. Build

Claude Code or Codex: open the terminal, go into the folder, run claude or codex, and paste the request. Accept only file creation inside the folder.

ChatGPT: paste the request, copy the code you get back, save it as index.html in the folder (Notepad, "save as", type "all files"), and double-click it.

DoneThe form opens in the browser, you add 3 orders, and you see the list with the total.

3. Use it and push it

Place 3 normal orders. Then try: quantity 0, negative price, a name with 500 letters, an empty field, and open the "manager area".

Write down everything the app accepted that it shouldn't have.

4. Look for flaws

Open the code (in the browser: right-click, "View page source", or Ctrl+U). Search for CHAVE, senha, and gerente.

Open a new conversation, paste the code and the audit prompt. Check in the code every flaw it lists: the AI makes things up too.

Key questionIf anyone opens this page, what can they see and do?

03 · Templates to copy

The rules, the app request, the audit, and the list of flaws.

Practice rules (paste before anything else)
Rules for this test:
- Work only inside this folder. Do not delete anything outside it.
- Use only made-up data. No real name, CPF, or phone number.
- Do not publish anything on the internet and do not install anything outside the folder.
- The only key allowed is the fake one: CHAVE-DE-TESTE-123.
- At the end, tell me what you created and how I open it.
App request (1 screen)
Create a one-screen app, in a single index.html file that opens directly in the browser, with no server.

It is the order form for Horizonte Distribuidora (cleaning products):
- Fields: customer, product (list with 5 made-up products and prices), quantity.
- An "Adicionar pedido" button. Below it, the list of orders with the total in R$.
- Save the orders in the browser itself, so they don't disappear on reload.
- An "Área do gerente" button that shows all orders and lets me delete them.
- When adding, "send" the order to the stock API using the key CHAVE-DE-TESTE-123 (it can be just simulated).

Simple look, readable on a phone. Explain in 5 lines how the app works.
Audit prompt (new conversation)
You are a security reviewer. Analyze the code below, from an app built with AI.
Look for, in this order:
1. Keys, passwords, or tokens visible in the code that runs in the browser.
2. Areas or actions that should require login and don't.
3. Data that anyone with the link can see or delete.
4. Unvalidated inputs (quantity 0, negative price, huge text, code in the field).
5. External libraries: which ones, where they come from, and whether the version is old.
6. Personal data stored without need.

For each flaw: what it is, the line or snippet, the severity (high/medium/low), and how to fix it.
Don't make things up: if you can't confirm it from the code, say "not confirmed".

Simulation: illustrative example
  • Key in the browser code: the CHAVE-DE-TESTE-123 shows up in Ctrl+U. If it were real, any visitor could copy it.
  • Manager area without login: a button open to everyone that deletes orders.
  • No validation: it accepts quantity 0 and negative price; the total comes out wrong.
  • External library loaded from the internet, with no pinned version.
  • Thinking "it worked" = "it's safe": the app opens and has a serious flaw.
  • Auditing in the same conversation that built it: the AI tends to defend its own code. Use a new conversation.
  • Accepting the AI's list without checking: it may point out a flaw that doesn't exist or miss a real one.
  • Publishing "just to show": what is on the internet, anyone can find.

04 · Why this matters outside the classroom

In May 2026 the security firm Red Access said it found about 380 thousand public pages and apps built with tools like Lovable, Replit, Netlify, and Base44; about 5 thousand of them exposed possibly sensitive information, such as financial documents and customer-service conversations. The platforms disputed part of that reading: a visible public app is not, by itself, a leak.

The lesson for you doesn't depend on who is right: anyone who builds fast with AI needs to ask, before publishing, who can see and do what. That is exactly what this lesson trains and what lesson 4 asks for in the lab company.

05 · Practice: build and audit

About 60 minutes in total. Do it in order.

E1 · Folder and rules

5 min

Create the teste-horizonte folder and paste the practice rules at the start of the conversation with the AI.

Done when: the folder exists and the AI confirmed the rules before building.

E2 · The app running

20 min

Use the app request on the path you chose. Open index.html in your browser and register 3 orders.

Done when: the app opens in your browser and shows 3 orders with the total in R$.

E3 · Use it and abuse it

10 min

Test quantity 0, negative price, empty field, huge text and the manager area.

Done when: you wrote down what the app accepted that it shouldn't have (or that it rejected everything).

E4 · Audit and list of failures

25 min

Look in the source code, run the audit prompt in a new conversation and check each item in the code.

Done when: the list has 3 failures, each with the line or screenshot of where it is and how you found it.
